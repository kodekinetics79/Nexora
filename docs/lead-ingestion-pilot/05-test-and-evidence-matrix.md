**Zero PDF. Zero DOCX. Zero XLSX. Zero JPEG/PNG. Zero EML. Zero MSG.**

Six of the pilot's 24 required scenarios are format-acceptance scenarios over exactly the formats
that have no fixture. The pilot cannot be accepted from the current corpus, and no amount of test
authoring closes this — it is a **data** dependency (charter A7), not a coding task.

Where fixtures do exist for other formats, they are **generated by the test that consumes them**.
`RealDocumentBenchmarkTests.cs:23-49` says so in its own words, and the admission is worth quoting
because it is the single most honest comment in the repository:

> *"Every fixture is generated by this file, so the 'expected token' is a string this test planted

> 'criticalFieldAccuracy', alongside 'localLeadRate=100%', 'localPageRate=100%',
> 'localFieldProcessingRate=100%' and 'externalDependencyRate=0%' — four hardcoded literals that
> were not computed from anything at all … Read out of context those numbers looked like a measured
> 100% extraction accuracy across a real corpus. **They measured nothing.**"*

That file has already been de-fanged (it no longer emits a percentage) and renamed away from
"benchmark" in its documentation. **Credit where due: this is the correct remediation.** It is
recorded here so the fix is not silently undone, and so nobody re-reads the old numbers from git
history as if they were evidence.

### 2.2 FINDING Q2 — SEVERITY: HIGH. No test proves the LLM extracts anything.

The LLM is abstracted behind `ILLMService`

Ten test files, **~138 test methods**, consume these stubs:


The canonical fixture is `Ext.Result(...)` at `ExtractionFakes.cs:169-183`, which hardcodes
`Rfqno: "RFQ-1"`, `BuyersName: "Buyer"`, `RecDate: "2026-07-14"`. **Not one assertion in the suite
compares a model's output against a real document's true contents.**

**The honest characterisation, in both directions:**

- **What these tests genuinely prove, and it is not nothing:** chunk planning and boundary
  arithmetic; retry and idempotency-key discipline; line-level quarantine; conservation of item
  counts through the pipeline; governance/allow-list enforcement at the pre-egress boundary; the
  extractor's response to a truncated model reply. `BudgetedStubLlm`'s docstring
  (`ExtractionFakes.cs:70-81`) states it models the way `ollama.com/deepseek-v4-pro` *actually*
  failed on a 40-line RFQ — `done_reason="length"`, no parseable JSON. That is a fake built from an
  observed production failure, which is the right way to build one. These are the parts of the
  pipeline that broke repeatedly in production, and they are now well covered.
- **What they cannot prove:** that the model reads a real RFQ correctly. Everything downstream of
  the model is tested; the model itself is assumed correct by construction.

**Consequence for the pilot.** Extraction accuracy cannot be asserted from the test suite at any
confidence. It can only come from labelled ground truth. The product already knows this and has the
machinery: `AccuracyMeasurementService` with a Wilson lower bound and a 30-document floor, tested at
`ExtractionAccuracyMeasurementTests.cs:29-46`, with two tests existing specifically to prove the
product **refuses** to emit a percentage it has not earned. That is the correct design.

**But the input to it is empty.** `LeadReviewAudits` has **0 rows** in production (verified
2026-08-06 02:20 UTC) — no human has ever completed a review, so no labelled corpus cell exists, so
no accuracy figure can be computed today. **Accuracy is not low; it is undefined.** Saying anything
else to a client would be the overclaim the design exists to prevent.

### 2.5 FINDING Q4 — SEVERITY: MEDIUM. The default browser lane runs against a fake API server.

Even the "0 mocks" specs do not necessarily hit the real backend, because the **default** Playwright
configuration starts a hand-written Node fake in place of ASP.NET Core.

`Frontend/playwright.config.ts:6` — the default is fixture mode:

```ts
const fixtureMode = process.env.E2E_FIXTURE_MODE !== 'false';
```

`Frontend/playwright.config.ts:122-127` — in that mode a fake API process is launched:

```ts
webServer: startWebServer ? [
  ...(fixtureMode ? [{ command: 'node e2e/support/fixture-server.mjs', url: `${apiURL}/health`, … }] : []),
```

`Frontend/e2e/support/fixture-server.mjs` (12.7 KB) serves canned leads, RFQs and quotes, and mints
its own **unsigned** JWTs — `fixture-server.mjs:28-31`:

```js
const encode = (value) => Buffer.from(JSON.stringify(value)).toString('base64url');
return `${encode({ alg: 'none', typ: 'JWT' })}.${encode({ sub: String(role.id), … })}.fixture`;
```

Its canned lead (`fixture-server.mjs:36-45`) carries `aiconfidence: 0.98`,
`customerMatchStatus: 'Matched'`, `commercialFactsVerified: true`, `itemCount: 1` — **none of which
is reproducible in the real system today** (production `AIConfidence` ranges 0.09–0.76 and
`Leads.CustomerID` is populated on 0 of 51 rows).

**So `npm run e2e` green means the React app renders correctly against a fake.** It is a real and
useful UI regression net. It is not backend evidence, and it must never be cited as pilot proof.

There is a guard rail worth noting: `playwright.config.ts:81-83` refuses to run fixture mode against
anything but loopback, and `:13-30` requires 24 named env vars before `E2E_ACCEPTANCE_MODE=true`
will start. The separation between "fixture" and "acceptance" is deliberate and correctly enforced.

### 2.6 FINDING Q5 — SEVERITY: MEDIUM. Tests that assert code paths rather than outcomes

`AuthoritativeEvidencePostgreSqlTests.cs` (17 tests) and `ChunkedExtractionServiceTests.cs`
(32 tests) both assert on `StubLlm.CallCount`, `StubLlm.IdempotencyKeys` and
`StubLlm.RequestedItemCounts` — i.e. **on the shape of the calls the code made**, not on the data
that came out. `ExtractionFakes.cs:27-32` is explicit that this is the intent:

```csharp
/// <summary>The governed idempotency key of each successive call, in order — the proof
/// of exactly which (job, attempt, chunk) request the extractor issued.</summary>
public List<string> IdempotencyKeys { get; } = new();
```

This is legitimate for the property under test — idempotency **is** a property of the call sequence,
and the retry-idempotency defect in the charter was exactly a call-sequence bug. It is recorded not
as a defect but as a scope limit: these tests would still pass if the model returned garbage.

### 4.2 Execution rules for Phase 4

1. **No scenario passes on fixture mode.** `E2E_FIXTURE_MODE=false` or it is not evidence.
2. **Every pass needs an artefact** — Playwright trace/video/HTML report, or a SQL result set with
   its query and a UTC timestamp. A green console line is not an artefact.
3. **Ground truth is human-keyed before the run**, never read back from the system's own output.
4. **Re-run the baseline lanes** (§1) before declaring any scenario complete; the delta from
   2521/2521 must be zero or explained.
5. **A refusal can be a pass.** T-02, T-05, T-08, T-21 pass on a truthful, visible refusal. Silent
   success on unreadable input is the failure mode this pilot exists to prevent.

### 5.2 What this number does and does not say

**It says:** the pipeline now takes 30 real documents from upload to persisted lead with correct
line-item counts and zero silent loss. Given that charter §5 records 1,133 successful AI calls
producing **zero** leads three days earlier, this is the first clean end-to-end drive the system has
ever completed. Two transient blocks were observed and self-cleared during the run — jobs 41 and 54
sat in `Pending` with `"External AI dependency policy would exceed 10%; route this occurrence…"` at
02:19 and had both completed by 02:33 — which is the AI governance ceiling behaving as designed
(deferring, not destroying) rather than the pre-fix behaviour of discarding authorized results.

**It does not say the extraction is accurate.** This is a *completion* rate, not an *accuracy* rate.
It proves no document was lost and no line count was fabricated. It proves nothing about whether the
extracted part numbers, quantities and manufacturers match the documents. Per §2.2, accuracy remains
**undefined** — `LeadReviewAudits` = 0 rows, so no labelled ground truth exists and
`AccuracyMeasurementService` correctly refuses to emit a figure.

**Do not present 100% to a client without that qualifier.** "30 of 30 documents processed
end-to-end with no loss and exact line-item conservation" is true and defensible. "100% extraction
accuracy" is the overclaim this program exists to prevent.

Attempt counts are also worth recording honestly: succeeded jobs carry 1–15 attempts (median ~14 for
the 02:02–03:33 batch). The pipeline is now reliable, but it is reaching success **through retry**,
not on first pass. Cost-per-document (charter A5) must be measured against attempts, not documents.
